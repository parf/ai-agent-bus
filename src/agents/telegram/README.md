# The Telegram agent

📌 **TL;DR:** Telegram serves itself while a long poll receives bot updates.
It bundles the shared session router and subscription/filter code; receive
history and routes persist through the agent's own KV.
User instructions live in the [Telegram guide](../../../docs/agents/telegram.md).

## Setup

See [bot and runner setup](../../../docs/agents/telegram.md#installing-it).
`package.sh` emits a flat telegram.js, filter-worker.js and agent.json package;
no runtime import may reach the checkout. Both Slack and Telegram bundle
`../shared/router.ts`, with Telegram retaining numeric message ids.

## Methods

## Receiving and forwarding

The receiver restores its offset, rings and directories with transient-read
retries. Corrupt array caches log the key and start empty. Seen state follows
handler success, definitive refusal or bounded retry exhaustion. Dirty keys
flush before the durable offset advances; a failed flush does not redeliver
a successfully handled message. Full cache snapshots are written periodically.
Bot-authored messages remain in history but do not enter routing/forwarding.
The shared filter worker bounds subscription evaluation and disables slow filters.

## Reply routing

See the [user contract](../../../docs/agents/telegram.md#reply-routing).
The common router serializes KV snapshots with concurrent posts and callbacks.
It publishes a dispatched bus-id mapping before classifying fast session answers.
Explicit re replies require that id; MCP-shaped answers use a random-UUID
correlation plus the mapped sender. The TypeScript-only matchesReply/onReply
options share the existing serving reader and worker/drain budget.

## Per-chat routing

See [chat and channel settings](../../../docs/agents/telegram.md#per-chat-routing).
`channel_post` is adapted at reception; channel-admin announcements require a
configured channel route. Own channel publications are suppressed by their map.
Dictionary access never accepts inherited properties.

## The pinned HTTP policy


Every Telegram call runs inside the caller's deadline: a 429 waits
`parameters.retry_after` (at most 30 s) and retries the write once if the
wait and the retry still fit, a write is never retried otherwise, and a
read retries once on 5xx. A 409 — another poller or a webhook on the
token — is logged with its description and named by `whoami`.

## Verification

The slow agent_telegram shard includes receive durability/retries, fake API
HTTP policy, routing scopes and prototype boundaries. TG.9/TG.10 routing tests
remain unchanged across the shared extraction. The Slack S.10 real-daemon
fixture also executes both packaged agents outside the checkout and calls
Telegram whoami. MCP reply and premature-seen mutants fail named assertions.

## Authored help

`agent.json` owns methods, typed arguments and Configuration descriptions.
`env.dist` owns environment-key comments. Package help is generated by the runner;
self-serving and bare-process help uses the shared manifest helper instead of
a second method list. Bundled agents omit `version` and use the bus version.
Executable-grammar checks compare the methods with generated help.

On SIGTERM/SIGINT the bus drains accepted calls, the receiving HTTP request
and rate-limit/backoff waits are cancelled, and the bus transport closes.
Intentional poll cancellation is not a poll error. `shutdown.test.ts` holds a
real fake-API request open and checks that SIGTERM exits within 1.2 seconds.
