# Issues — Nov 17, 2026 · wiki RAG setup

Found while connecting `/home/parf/wiki` to `#rag/wiki` through `#filescan/wiki`, with the owner's setup script `tmp/scripts/wiki-rag-setup.sh`. A guide that covers every step and each issue below is the follow-up: `setup-rag.md`.

## FileScan

- ✅ J131 `sub add` starts no delivery round, so a new subscription sends nothing until the next poll tick or file event.
  - Evidence: `src/agents/filescan/filescan.py`, the `sub.add` branch returns `self.subs.add(…)` without calling `_round()`. The `scan` branch does call it. Live: `sub add #rag/wiki as rag wiki pages` answered `sent 0`, and `status` showed `pending 122` with an unchanged `last_scan` until the wiki agent called `scan`.
  - Impact: with the default `every` of 30 minutes, the initial load in [filescan](../../../docs/agents/filescan.md#what-it-does) ("A first run that feeds the whole existing folder") starts up to 30 minutes late, and looks stuck meanwhile.
  - Fix: run one round after a replaying `sub add`, bounded as `scan` is.
  - Done: a replaying `sub add` asks the timer for a round at once (`_kick_round`).
- ✅ J132 A backlog drains one batch per round, and rounds come only from a tick, a watch event or `scan`, so a large initial load crawls.
  - Evidence: `src/agents/shared/change_sync.py` `deliver()` sends "at most `batch`" per subscriber per round. `filescan.py` `tick()` runs one `_round()`. The default `batch` is 20 and `every` is 30 minutes, so 122 files take about 7 ticks, roughly 3.5 hours, unless someone calls `scan` repeatedly.
  - Impact: the documented `max_per_scan` (200) suggests up to 200 files per scan; delivery is actually 20 per round.
  - Fix: keep running rounds while a subscriber confirmed a full batch and the round deadline allows, or start the next round at once while a backlog remains.
  - Done: a round that moved something and left more pending asks for the next round at once, without walking the folder again; a round that moved nothing waits, so a down target never spins.
- ✅ J133 One file that RAG refuses blocks every later file of that subscriber.
  - Evidence: `change_sync.deliver()` "stops at the first one not confirmed, so order holds". In `filescan.py`, `_confirm()` returns False on an `error:` reply and only records the reason in `skipped_for_rag`. Live: the first file in key order (`AGENTS.md`) was refused with `classification prompts are not configured`, and every round stopped there: `sent 1, confirmed 0, dropped 1, pending 122`.
  - Impact: a permanent refusal of one file stalls the whole subscription silently. [When RAG's answer is lost](../../../docs/agents/filescan.md#when-rags-answer-is-lost) says "A refusal is a definite answer: the file goes again on the next round", which reads as harmless.
  - Fix: let a refused upsert step aside, as a `settle`-unknown row does, so the rest of the batch goes on, and warn once by name. At least document the head-of-line effect and surface it in `status`.
  - Done: `ok` may answer `REFUSED` in `change_sync.deliver()`; the change stays pending, the batch goes on, and `later` puts refused paths behind every fresh one.

## RAG

- ✅ J134 An upsert is refused until its table has classification prompts, and every upsert makes a paid Jev call. Neither the RAG install steps nor FileScan's `as rag` path says so.
  - Evidence: `src/agents/rag/core.py` `prepare()` and `upsert_large()` raise `classification prompts are not configured` when `repo.prompt('get', table)` is None, then call `self.backend.decide(…)` for labels. The `classify` config flag gates only the standalone `classify` method (`core.py:69`).
  - Docs: [installing RAG](../../../docs/agents/rag.md#installing-it) ends at collection, grants and Configuration. FileScan's [Try this first](../../../docs/agents/filescan.md#try-this-first) shows `sub add … as rag` with no prompts step.
  - Impact: a fresh instance cannot store anything. Each stored file costs an `#ai` call as well as an embedding, which a cost estimate based on embeddings alone misses.
  - Fix: name prompts as a required install step, and in FileScan's `as rag` docs. Decide (owner) whether a table may store without classification.
  - Done: install step 5 and FileScan's Try this first name the prompts and the paid call. Misconfiguration answers now name the field or the fix (`required field X is missing`, `unknown field X`, `… set them with method prompts, action set`, the missing index names, the grant to add). Storing without classification stays an owner choice.

- ✅ J138 A block's refusal reached RAG's caller as `voyage refused the request`, without the block's reason.
  - Evidence: `src/agents/rag/blocks.py` `invoke()` dropped the block's answer text. Live: 17 wiki files were refused during the first load as `ai`, `voyage` or `qdrant refused the request`, and most went through on a retry, which points to rate limits nobody could see.
  - Done: the refusal carries the block's own reason, `voyage refused the request: 429 …`.

## Schedules

- ✅ J139 A scheduled message carries no roles, so a schedule cannot call a role-gated method, even when its creator holds that role.
  - Evidence: the wiki agent holds `read` on `#filescan/wiki`, and its own `status` call works. Its schedule `d8f919bf9298` (target `#filescan/wiki`, body `status`) fired from `#bus` and got `forbidden: This call needs a direct instance role`. [Schedules](../../../docs/03-records-schedules.md#who-may-use-them) check only the creator's may-send.
  - Workaround: schedule a wake-up to the creator itself, which then makes the call under its own name.
  - Owner choice: should a firing deliver the creator's roles on the target (checked at each firing, as may-send is), or stay role-less and be documented so?
  - Done (owner chose: the creator's roles): each firing carries the roles the creator holds on the target at that firing, worked out in `send` like may-send, so a revoked grant is gone from the next firing.

## Setup

- ✅ J135 Connecting one folder to a dedicated RAG takes about fifteen owner steps across two runners, with no single command or guide.
  - Evidence: `tmp/scripts/wiki-rag-setup.sh` and `wiki-rag-prompts.sh`. The steps are:
    1. Register two records.
    2. Create one Qdrant collection and eight payload indexes.
    3. Grant `#qdrant`, `#voyage` and `#ai`.
    4. Set two Configurations and the table prompts.
    5. Add two runner inventory entries, including a `roots` entry.

  - Impact: each step is a chance to miss one, and the misses found here are J131–J134.
  - Fix: a `setup-rag.md` guide covering the order, the owner-only steps, the costs and these issues; later, perhaps one setup command.

At the Nov 16 boot it started before the daemon socket existed, failed 5 times and stayed `failed` until `systemctl --user reset-failed` and `start` on Nov 17.
  - Impact: every user-runner agent (`#filescan/*`, `#tmux-sessions*`) is silently absent after a slow boot.

  - Done: the unit template (`user_runner.go`) restarts every 30 seconds with no start limit. An installed unit changes at the next `agent-bus-setup` run.
