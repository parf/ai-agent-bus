- ✅ J66 the T-19 landing (`d303a43f`, docs only) was red on its first normal run: `go_unit` went over the 15 s fast ceiling (15.115 s wall)

The first inspection found 2746 files dated 2026-11-01 10:xx and a directory mtime of 10:14:17, when the gate started. - ❓ 🟠 J67 the db agent package failed to rebuild in the 0.9.250 deploy, so the old package stayed live
  - Owner: `#ab-lead1` (fixed by `#ab-w1b`).
  - Evidence: `src/agents/db/package.sh` read pymysql, psycopg and psycopg-binary through `importlib.metadata` and iterated `distribution(...).files`. On the deploy host psycopg's metadata was gone and the system pymysql 1.1.2 had no `RECORD`, so `files` was `None` and the loop raised `TypeError`. No other packager reads host metadata (`grep -l importlib` over `src/agents/*/package.sh`: only `db`).
  - Impact: the db package could not be rebuilt on a host whose Python packages differ from the author's; the deployed copy (pymysql 1.1.3, psycopg 3.3.6) kept running.
  - Fix: the drivers install from `requirements.txt` (exact versions, wheel SHA-256 hashes, `--no-deps --only-binary`), never from site-packages; `AB_DB_WHEELS` serves an offline build. The rebuilt tree is byte-identical to the deployed package (141 files compared) apart from the host-only `REQUESTED` markers. The old `files is None` path no longer exists, so its mutant is the install failure hidden by `|| true`.
  - Proof: `agents/db/test_package.py` builds from synthetic hashed wheels under a host whose metadata has no `RECORD`; before the fix it failed (host metadata used), after it passes 2/0. Mutants red on assertions: the old script, the cleanup removed, a failed install hidden.

- ❓ J69 `TestSmokeInterruptStopsItsTimeoutShard` flakes inside a full slow run
  - Owner: `#ab-dir` schedules it (found by `#ab-w2b`).
  - Evidence: in the slow pass on `36d43221` (62 shards), `go_unit` "go race" failed with `smoke_driver_test.go:77: the fixture shard did not start` after 3.01 s. The same test passes 3 of 3 alone with `go test -race -count=1 ./cmd/agent-bus -run TestSmokeInterruptStopsItsTimeoutShard` (1.06 s each).
  - Impact: a start-timeout under load, in a smoke-driver test that no recent change touched; it can turn a slow run red once.
  - Cause: the test waited for the fixture shard's own pid file, but only for a fixed 3 s, with no sign of why it was late; a loaded host (a 62-shard slow run) can start a shard later than that. CPU hogs alone did not reproduce it here (the driver start is 0.05 s alone, 0.39 s beside 40 hogs on one CPU), so the red is reproduced by delaying the fixture shard's start instead.
  - Fix: `smokeStartWithin` is 30 s and the wait ends at once, printing the driver's output, if the driver itself exits; the exit wait after SIGTERM is 15 s. `TestSmokeInterruptWaitsForALateShard` starts the shard 3.5 s late.
  - Proof: with the old 3 s wait that test fails with `the fixture shard did not start` at 3.01 s, the reported symptom; with the fix both interrupt tests pass under `-race`.

- ❓ 🟠 J71 the T-20 2d landing went red once in `agent_logwatch`, then green on rerun
  - Owner: `#ab-lead2` (found by `#ab-w1b`; the J69 start flake is not this).
  - Evidence: `tmp/gate-logs/20261101-120130-T-20.log`, first run `passed 1269, failed 1` (line 4354), rerun `passed 1270, failed 0` (line 8690). The failure is `test_author_is_checked_for_target_and_source_at_add_and_each_copy` (`test_logwatch.py:283`): `'subscription: filter_timeout' != 'subscription: admission_unavailable'`. The two runs took about 60 s and 59 s, so the 124 s is both runs together, not one run over the ceiling.
  - Cause: `src/agents/shared/subscription_filters.py` evaluates a filter under `signal.setitimer(ITIMER_REAL, min(.05, ...))` with a 0.9 s budget per batch. That is wall-clock time: on a loaded host a trivial match such as `/error/i` against `ERROR unavailable` can be descheduled past 50 ms, the filter reports `timeout`, and `subscriptions.py:279` drops the copy as `filter_timeout` before the admission failure the test expects. That run's shards ran 45–60 s side by side.
  - Impact: any subscription test (and a real filter on a busy host) can drop a match as a filter timeout without the filter being slow.
  - Proposed fix (in `src/agents/**`, left to its owner): measure the filter in CPU time (`ITIMER_VIRTUAL`) or retry a timed-out evaluation once before dropping; and have the test inject the budget instead of racing the host.
