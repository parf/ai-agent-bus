## Daemon

- ⏳ J39 a message was lost to a reader that had cancelled its wait
  - Evidence: replacing a reader (a runner reload that switches an agent's form) under CPU load lost one message in about three runs: the old poll's waiter was still registered, the daemon handed the next message to it, and the handler wrote the reply to a closed connection. The new reader was also refused ("inbox already has a reader") for the same stale waiter
  - Cause: a waiter stayed in the inbox until its handler noticed the cancel, and the consume handler replied whatever the consume returned, whether or not its caller was still there
  - Impact: a reload, or any client that drops a long poll and sends right after, can lose a message without an error
  - Fix (`ab-w2b/J39`): the waiter carries its poll's context; a message is never handed to a cancelled one and its leftover is not a second reader (`TestSendDoesNotHandAMessageToACancelledWaiter`, `TestCancelledWaiterDoesNotMakeTheNextReaderASecond`); a message handed to a poll cancelled meanwhile goes back to the front (`TestMessageHandedToAPollCancelledMeanwhileGoesBackToTheFront`); the consume handler peeks at its socket and requeues when the caller has closed it (`ConnContext`, installed by `agent-busd`)
  - Check: `TestReplacingAReaderLosesNoMessage` replaces a reader through a real server 150 times and counts each message delivered exactly once; 20 repeats under 48 busy loops stayed green. Mutants, each failing on an assertion: the waiter purge removed (`handed "keepme" to a cancelled waiter`), the admission purge removed (`inbox already has a reader`), the requeue removed (`want the message withheld`), the socket peek disabled (`delivered map[two:1]`, run 85). Deploying needs a daemon restart
  - Review fixes (#ab-w2a): the poll's transport answers "is my reader gone" at the moment a message would be handed (`core.WithAlive`, set by the consume handler), so the message is never handed and arrival order holds; a requeued reply gets its caller's reservation back, so the push adapter cannot take it (`TestRequeuedReplyKeepsItsReservationForTheCaller`); a requeued message goes back by arrival time, not to the front, so what a filtered read skipped is not jumped (`TestRequeuePutsAMessageBackInArrivalOrder`); the peek reaches the socket under a TLS conn and the dual listener's replay (`duallisten`'s `NetConn`), proved for the dual listener by the plain connection: without the unwrap the 150-run count fails. Mutants red: reservation not restored, requeue at the front, early gone-check removed, unwrap removed, hand-off check and handler peek both removed
  - Limits: two socket questions, both answered at once without reading: a peek that meets the end of stream (plain TCP, the dual listener's plain connection, unix sockets), and on Linux the kernel's TCP state, which has the peer's FIN even behind queued data (`TestTCPStateSeesThePeerCloseBehindQueuedData`); the second is what covers TLS, where the client's close_notify is data in front of the FIN and a peek reads it as alive (found by #ab-w1c under load: the TLS cases lost a message with the peek alone). Off Linux a TLS close is noticed only when the server reads it. Over https with HTTP/2 (the bus's own Go clients' default) a cancelled poll is a stream reset, not a close, so it is caught only by the server's own frame read (J41, below). A half-closed HTTP/1.1 client reads as gone: the poll answers 204 and the message is requeued, nothing is lost. Scale: every hand-off asks each waiter's `alive` (a `recvfrom` and a `getsockopt` per waiter under the bus lock); an inbox has few waiters, so it costs little, and it is the price to watch if waiters ever grow

- ⏳ J41 a poll cancelled over HTTP/2 can still lose a message to the cancelled waiter
  - Evidence: J39's delivery count passes over plain TCP, the unix socket and TLS with HTTP/1.1; over https with HTTP/2, the Go clients' default, the cancel is a stream reset frame, so neither a peek nor the kernel's TCP state sees it, and a message sent in the window before the server reads the frame can go to the gone waiter
  - Impact: the same loss as J39 for a runner or client that reaches the daemon over https with HTTP/2 and replaces a reader
