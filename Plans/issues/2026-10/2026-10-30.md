## Access

- ❓ ⚪ J24 with TLS on, the daemon's port also answers plain HTTP, and nothing refuses plain HTTP from a remote host
  - Evidence: `src/internal/duallisten/duallisten.go:1-4,81` sniffs each connection and hands any first byte other than `0x16` on as plain HTTP; `src/cmd/agent-busd/supervisor.go:53` logs "TLS offered on <addr> beside plain HTTP"; [setup § TLS](../../../docs/07-setup.md#tls) says "The port answers TLS beside plain HTTP". Off loopback the daemon only warns once at start (`supervisor.go:44`). The client never falls back: an `https://` address is refused on a TLS error, never retried as plain HTTP (`src/internal/api/dial_tls.go:26-29`)
  - Impact: a node set up with TLS still accepts a token and message bodies sent over plain HTTP from any host that reaches the port, for example a client configured with `http://` by mistake; the node cannot be made HTTPS-only for remote callers. The default listen address is loopback (`127.0.0.1:6767`), so this applies once an operator sets `--addr` off loopback
  - Settled by: owner — whether a node with TLS should refuse plain HTTP from non-loopback peers, and whether that is a setting
