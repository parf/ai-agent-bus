# 0.7 performance baseline

📌 **TL;DR:** What 0.6 costs before the SQLite store, measured by
`src/internal/baseline` at 1k, 10k and 100k records. Reads and traffic are
flat with registry size; a one-field management edit is not, because 0.6
rewrites the whole snapshot for it. [K.17](0.7.0-TODO.md#delivery-and-release)
reruns the same benchmarks and compares.

## How it was run

| | |
|---|---|
| Code | 0.7.0, behaviour identical to 0.6.17 |
| Host | AMD Ryzen 9 5900X, 24 threads, Linux, local disk |
| Toolchain | go1.26.5 linux/amd64 |
| Command | `cd src && go test ./internal/baseline/ -run '^$' -bench . -count 1` |
| Shape | n Agents owned by one User, each admitting the reader through a group; backlog spread over the first inboxes |

## Results

| Operation | 1k | 10k | 100k |
|---|---|---|---|
| Lookup, authorized through a group | 0.83 µs | 0.86 µs | 0.92 µs |
| List, whole caller-visible registry | 0.77 ms | 7.2 ms | 105 ms |
| Send + consume | 1.5 µs | 1.5 µs | 1.6 µs |
| Send + consume, 10k messages queued elsewhere | 1.6 µs | 1.5 µs | 1.6 µs |
| Send + consume, all CPUs, one inbox each | 1.9 µs | 1.9 µs | 1.9 µs |
| Manage one field, durable | 1.4 ms, 151 KB written | 13.8 ms, 1.35 MB | 155 ms, 13.5 MB |
| Manage one field, 10k messages queued | 13.6 ms, 2.2 MB | 27.9 ms, 4.0 MB | 170 ms, 16.2 MB |

Allocations: lookup 3, send + consume 4, list one per visible record, manage
roughly one per record plus one per queued message.

## What 0.7 must change

| Figure | Target |
|---|---|
| Manage write volume | the edited record, not the registry and backlog ([K.3](0.7.0-TODO.md#storage-and-identity)) |
| Lookup and send + consume | no regression; registry and authority reads stay in memory |
| List | no regression; it is linear in visible records by nature |

The concurrent figure is one node lock shared by every inbox. Run with
`-mutexprofile` to see where it waits; K.17 records contention the same way.
