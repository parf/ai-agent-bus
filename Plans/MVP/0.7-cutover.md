# Clean reinstall for 0.7

📌 **TL;DR:** Install 0.7 with fresh SQLite state; do not migrate 0.6 data. The
product has no production deployment, so the transition is a clean reinstall:
old snapshots, credentials and backlog are not imported, and no conversion
tool is written.

## Scope

Owner decision, September 21, 2026: the product has no production deployments.
The 0.7 transition is a clean reinstall, replacing the previously planned
inventory, ownership mapping and offline state rewrite. No 0.6 state-preservation
or conversion tool is required. This follows the existing pre-1.1 compatibility
policy; the historical [0.6 cutover](cutover.md#the-procedure) is unchanged.

[K.1 and K.1.4](0.7.0-TODO.md#storage-and-identity) track preparation and setup;
[K.17](0.7.0-TODO.md#delivery-and-release) owns installed acceptance.

## Procedure

The reinstall is one explicit setup action, `sudo ./agent-bus-setup --reinstall`,
run from the unpacked 0.7 archive (or, on a development checkout,
`src/git-install.sh --reinstall`). It never happens as a side effect of a start
or an upgrade.

| Step | What happens |
|---|---|
| 1. Stop | `agent-busd` is stopped; a node that cannot be stopped is not reinstalled |
| 2. Set aside | Everything in the daemon home, including the 0.6 `dump.json`, `token` and `.ssh/authorized_keys`, moves to a root-only `daemon.before-0.7-<time>` directory beside it. Nothing there is read again; it is kept only so an operator can look at what was there |
| 3. Install | The 0.7 release is installed as on a fresh host, and the unit is rewritten for the database |
| 4. Initialize | `agent-busd -init` runs once as the daemon account and creates an empty database; the unit itself never creates one |
| 5. Bootstrap | The daemon Owner is the installer's bare account name ([names](../../docs/01-identity-and-roles.md#names)); the installer's account and the runner account are mapped to local sockets; the installer's public key becomes the first user through the admin program, as on a fresh install |
| 6. Start and check | The daemon starts and setup waits until its public identity reports the 0.7 release |
| 7. Reconnect | Clients get new credentials: launchers and CLI users on the host take theirs from their account sockets on the next start; remote users ask again over SSH or by key. Old tokens authenticate nothing |
| 8. Recreate | Users, groups and records are created again through the ordinary 0.7 paths, so every one satisfies current ownership, status and private-value validation |

A failed or incompatible existing database is never silently replaced: the
daemon refuses to start on it, and only `--reinstall` sets a database aside.

## Verification

Exercise both a fresh host and replacement of a stopped 0.6 installation.
Prove that old credentials and backlog are not imported, the new Owner can
administer the node, and newly configured clients can exchange messages.

Once populated through 0.7 APIs, verify SQLite backup/restore, graceful restart,
bus-child crash recovery and failed-update recovery with matching 0.7 state and
binaries. These remain durability requirements; clean reinstall only removes
the obligation to migrate 0.6 data. Check file isolation and retain the required
installed browser, SSH and live-runtime acceptance evidence.
