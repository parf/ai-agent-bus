# Cutover to 0.7 persistence and ownership

📌 **TL;DR:** Inventory the stopped 0.6 node, require every ambiguous ownership
and incompatible credential decision explicitly, write a separate SQLite
candidate, validate it, then activate state and matching binaries together.

## Scope

This is the required implementation shape for
[K.1 and K.1.4](0.7.0-TODO.md#storage-and-identity). It follows the earlier
[record-kind cutover](cutover.md#the-procedure) but does not modify that
historical runbook.

The running 0.6 snapshot is never edited in place. The cutover keeps an
untouched snapshot, credential store and matching binaries as one rollback unit.
The daemon is stopped before inventory and remains stopped until the candidate
passes the target loader's validation.

## Inventory

The read-only report names, without printing private bodies:

- every object whose Owner is not an existing User, including self-owned and
  Agent-owned records;
- every credential whose principal is not a User or Agent, by principal and
  fingerprint;
- every Service whose stored secret does not satisfy the new env-file grammar,
  by Service and digest rather than body;
- every record or field the 0.7 model cannot represent;
- IDs, status, ACL, Maintainers, Groups, private-value digests, queue counts and
  durable per-queue counters used by the after-cutover comparison.

A fixture containing a self-owned Agent record, a Service credential and an
incompatible record must report all three independently. The tool also emits an
Owner-mapping template containing every affected object's stable ID and name,
with the replacement Owner blank. The completed file must preserve that object
set exactly; a missing, extra, renamed or duplicate object refuses the rewrite.

The report, mapping template and completed mapping are sensitive policy files.
They use the same daemon-account boundary as the database and backups: private
parent directory, mode `0600`, and no body for a token, secret, configuration or
message. A second account reading any artifact fails acceptance.

## Explicit decisions

The operator completes two inputs to the rewrite:

1. the emitted mapping template, assigning every listed object to an existing
   active User;
2. an explicit removal entry for every Queue, PubSub or Service credential.

No Owner is inferred from spelling, current Maintainers, ACL membership, a host
account or the caller running the tool. No incompatible credential is silently
converted or discarded. A missing or extra entry refuses the rewrite.

Users are never removed. Compatible User and Agent credentials retain their
principal and fingerprint. Removing an Agent or record deletes every stored
ACL, Maintainer, Group-member and Deliver-To reference to its name, so later
name reuse inherits nothing. A Service whose
existing secret fails the env-file grammar cannot enter the candidate; the
operator replaces it with valid content or removes it before activation. There
is no grandfathered legacy value.

## Rewrite and activation

The offline tool reads the preserved 0.6 inputs and writes a new SQLite
candidate. It carries each class separately:

- Users, including profiles, unique secondary identifiers, photos and enrolment
  public keys;
- the daemon Owner and the marker distinguishing established from absent;
- the local-account map and its established-versus-empty marker;
- records with compatible IDs, mapped ownership, status, ACL, Maintainers and
  every kind-specific field;
- Groups and membership, each carrying the `group` kind after the rewrite;
- compatible credentials and their lifecycle metadata;
- private configuration and secrets;
- queue contents and the four durable per-queue counters.

Every Agent name is rewritten with its `#` prefix as part of that rewrite —
the record's own `name` first, then every reference to it in an owner field,
ACL, Maintainers list, Group membership, Deliver-To and saved launcher
identity. User, Group and runtime terms are carried unchanged, and a term
matching no current entity is reported rather than guessed.

The JSON dump and credential file are input only; after activation SQLite is the
runtime store for all of those values.

The target loader validates the candidate before activation, including record
kinds, User ownership, credential kinds, queue-to-record compatibility, unique
secondary identifiers and derived indexes. Only then may setup switch the
configured state and binaries together. Failure restores the untouched 0.6
state and matching binaries; an old binary is never pointed at the new database.

## Verification

The before/after comparison checks each preserved class separately, matches
every reported removal to the operator's input, and confirms that every ACL,
Maintainer, Group-member and Deliver-To term naming an Agent carries the `#`
marker afterwards. One untyped Agent reference left behind fails its own check. Dropping any class from the
rewrite or any detection from inventory fails its own check. Installed
acceptance also exercises a failed validation, rollback, successful activation,
graceful restart and crash restart within the stated queue checkpoint window.
