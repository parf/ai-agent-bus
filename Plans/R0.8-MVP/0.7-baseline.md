# 0.7 performance baseline

📌 **TL;DR:** What 0.6 costs before the SQLite store, measured by
`src/internal/baseline` at 1k, 10k and 100k records, and what 0.7.13 costs on
the same host in the same session. A one-field edit went from a whole-snapshot
rewrite to 38 µs flat; send + consume is level; lookup and list are about a
fifth slower, the price of the per-call liveness and ownership checks the 0.7
model requires.

## How it was run

| | |
|---|---|
| Code | 0.7.0, behaviour identical to 0.6.17 |
| Host | AMD Ryzen 9 5900X, 24 threads, Linux, local disk |
| Toolchain | go1.26.5 linux/amd64 |
| Command | `cd src && go test ./internal/baseline/ -run '^$' -bench . -count 1` |
| Shape | n Agents owned by one User, each admitting the reader through a group; backlog spread over the first inboxes |

## Results

| Operation | 1k | 10k | 100k |
|---|---|---|---|
| Lookup, authorized through a group | 0.83 µs | 0.86 µs | 0.92 µs |
| List, whole caller-visible registry | 0.77 ms | 7.2 ms | 105 ms |
| Send + consume | 1.5 µs | 1.5 µs | 1.6 µs |
| Send + consume, 10k messages queued elsewhere | 1.6 µs | 1.5 µs | 1.6 µs |
| Send + consume, all CPUs, one inbox each | 1.9 µs | 1.9 µs | 1.9 µs |
| Manage one field, durable | 1.4 ms, 151 KB written | 13.8 ms, 1.35 MB | 155 ms, 13.5 MB |
| Manage one field, 10k messages queued | 13.6 ms, 2.2 MB | 27.9 ms, 4.0 MB | 170 ms, 16.2 MB |

Allocations: lookup 3, send + consume 4, list one per visible record, manage
roughly one per record plus one per queued message.

## What 0.7 must change

| Figure | Target |
|---|---|
| Manage write volume | the edited record, not the registry and backlog ([K.3](0.7.0-TODO.md#storage-and-identity)) |
| Lookup and send + consume | no regression; registry and authority reads stay in memory |
| List | no regression; it is linear in visible records by nature |

The concurrent figure is one node lock shared by every inbox. Run with
`-mutexprofile` to see where it waits; K.17 records contention the same way.

## 0.7 compared (K.17)

Run at 0.7.13 (`6f2f60f` plus the name-rendering change), and again at 0.7.0 in
a scratch worktree in the same session, three runs each, medians.

| Operation | 0.7.0 | 0.7.13 | Change |
|---|---|---|---|
| Lookup, authorized through a group, 1k / 100k | 0.86 / 0.95 µs | 1.04 / 1.26 µs | +21% / +33% |
| List, 1k / 100k | 0.78 / 112 ms | 0.99 / 135 ms | +27% / +20% |
| Send + consume | 1.58 µs, 4 allocs | 1.64 µs, 2 allocs | +4%, half the allocations |
| Send + consume, all CPUs | 1.9 µs | 2.1 µs | +12% |
| Manage one field, durable, 100k | 155 ms, 13.5 MB written | 38 µs, one row | −99.98% |
| Manage one field, 10k messages queued, 100k | 170 ms, 16.2 MB | 39 µs | −99.98% |

The management figure is the one 0.7 set out to change: an edit writes the
edited record, not the registry and backlog. Allocations are equal or lower
everywhere after names render in one allocation and an already-canonical name
is returned as given.

**Recorded tradeoff.** Lookup and list pay for checks 0.6 did not make: every
record answer asks whether the record and its User are active and whether the
caller still acts, and a listing asks it per record. Each is a few map reads;
together they are ~0.2 µs on a lookup and ~0.23 µs per listed record. Removing
them would mean caching authority across calls, which would let a revoked or
deactivated principal act on a stale answer — the failure the write-through
model exists to prevent. Accepted for 0.7; a per-call authority cache that is
invalidated by every commit is a [future candidate](../R2.0-Future/FUTURE.md#candidates).
